Quando CQRS é (e quando não é) a resposta

Antes de discutir CQRS, vale revisitar o que realmente é "complexidade essencial" num sistema de domínio. Boa parte das implementações que vejo são respostas a um problema acidental — geralmente acoplamento — disfarçado de problema arquitetural.

Toda vez que entro num projeto novo onde o time já se preparou para a minha visita, alguém em algum momento vai querer falar sobre CQRS. Já é um clássico. O sintoma normalmente é uma camada de aplicação inflada, um conjunto opaco de "services" que ninguém entende, e a sensação difusa de que "talvez precisássemos separar leitura de escrita".

A pergunta certa quase nunca é se você precisa de CQRS. É qual problema você realmente está tentando resolver — e se esse problema é resolvido por separação ou por outra coisa. Este ensaio é a minha régua, depois de implementar CQRS de verdade em três projetos da Leanwork e ter cogitado em outros dez antes de desistir.

O que estou chamando de CQRS

Antes de qualquer coisa, definição. Quando digo CQRS aqui, estou falando estritamente do padrão original do Greg Young: modelos diferentes para leitura e para escrita. Não estou falando de "ter uma classe Command e uma classe Query no mesmo handler". Isso é estilo de código, não arquitetura.

CQRS de verdade significa que o caminho que altera o estado do sistema e o caminho que consulta esse estado são artefatos separados: classes diferentes, frequentemente bancos diferentes, às vezes serviços diferentes. Os modelos não dividem nenhuma estrutura.

"A maioria dos sistemas se beneficia de ter dois modelos. A maioria dos times não está preparada para sustentar dois modelos." — um ex-CTO meu, em 2017

Sintomas que não são CQRS

Antes de discutir os casos onde CQRS resolve, vale eliminar o ruído. Existem três sintomas que frequentemente são confundidos com "preciso de CQRS" e que, na prática, são outra coisa:

  • Camada de serviços inflada. Isso é problema de organização interna. Resolve com pastas, contextos e disciplina — não com separação de modelos.
  • Consultas lentas. Isso é problema de índices, projeção e cache. Resolve com EF Core direito ou Dapper em queries específicas — não com event store.
  • Regras de negócio espalhadas. Isso é problema de modelo de domínio. Resolve com agregação correta — não com separação CQ.

Se você implementar CQRS pra resolver um desses três, vai sair do outro lado com os mesmos problemas mais uma carga operacional nova. É o pior dos dois mundos.

Régua prática

Se o time consegue articular qual problema CQRS resolve em uma frase, e essa frase contém "modelo de leitura" ou "consistência eventual", siga em frente. Se a frase contém "fica mais organizado" ou "melhores práticas", recue.

Onde a separação compensa de verdade

Existem três cenários onde a separação paga o custo — e raramente vejo CQRS aplicado por bons motivos fora deles:

3.1 — Reads e writes têm volumes radicalmente diferentes

O caso clássico: um sistema de catálogo onde 10.000 consultas acontecem para cada escrita. Separar o modelo permite otimizar leitura agressivamente — vistas materializadas, denormalização agressiva, cache de objetos prontos — sem comprometer o modelo de escrita.

3.2 — A leitura precisa cruzar contextos de forma cara

Quando uma única tela do produto precisa de dados de cinco bounded contexts diferentes, manter o modelo de leitura denormalizado e separado da escrita evita o pesadelo de orquestrar joins entre serviços ou contextos.

3.3 — O domínio é genuinamente event-sourced

Se você já decidiu por event sourcing (auditoria total, replay, etc.), CQRS deixa de ser uma escolha — é consequência. O modelo de leitura é a projeção, e o modelo de escrita é o stream de eventos. Aqui não há atalho.

Um exemplo concreto de como separamos comando e query num projeto financeiro recente:

// O comando — quem altera o estado.
public record ConfirmarPagamento(Guid PedidoId, decimal Valor);

public class ConfirmarPagamentoHandler : ICommandHandler<ConfirmarPagamento>
{
    public async Task Handle(ConfirmarPagamento cmd, CancellationToken ct)
    {
        var pedido = await _repo.CarregarAsync(cmd.PedidoId, ct);
        pedido.ConfirmarPagamento(cmd.Valor);
        await _repo.SalvarAsync(pedido, ct);
    }
}

// A query — modelo separado, otimizado para a tela.
public record PedidoResumo(Guid Id, string Status, decimal Total, string Cliente);

public class ResumoPedidoQuery
{
    public async Task<PedidoResumo> Run(Guid id, CancellationToken ct)
        => await _readDb.QueryFirstAsync<PedidoResumo>(
            "select * from pedido_resumo where id = @id", new { id });
}

Note que não há IRepository compartilhado entre os dois lados. O comando trabalha sobre o agregado real; a query trabalha sobre uma projeção achatada construída especificamente para essa tela.

Como manter o time são durante a transição

Se você decidiu que CQRS faz sentido, a parte difícil começa agora. Não é o código — é manter o time produtivo enquanto a estrutura muda. Algumas regras que vieram da minha experiência:

  • Não migre tudo de uma vez. Comece pelo bounded context que tem o desbalanço de leitura/escrita mais óbvio. Os outros podem esperar.
  • Mantenha consistência forte enquanto puder. Eventual consistency é uma decisão de produto, não técnica. Adie até que o cliente entenda.
  • Tenha uma estratégia de re-projeção desde o dia um. Você vai descobrir que projetou errado. Conviva com isso.
  • Faça pair programming agressivo nas duas primeiras semanas. O modelo mental novo é mais caro do que o código novo.

Critérios para reverter

Sim — em dois dos três projetos onde implementei CQRS, em algum momento revertemos parcialmente. Não é vergonha. O ponto é saber identificar quando o custo está maior que o benefício:

  1. Bugs intermitentes de consistência aparecem com frequência maior do que features.
  2. Devs novos levam mais de três semanas para entender o fluxo completo de uma feature.
  3. A maioria das histórias do sprint atravessa os dois modelos — sinal de que a fronteira está no lugar errado.

Se você bater dois desses três por mais de um trimestre, é hora de uma retrospectiva séria sobre se o problema que CQRS resolveu ainda existe — ou se ele resolveu o problema antigo e criou um pior.
